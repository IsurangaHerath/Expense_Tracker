# 3 System Features and Functional Requirements

## Requirement Format

All functional requirements follow IEEE format:
- **ID**: Unique identifier (FR-MOD-###)
- **Title**: Brief descriptive name
- **Description**: Detailed requirement
- **Priority**: Mandatory, Should, Could
- **Source**: User or system requirement
- **Acceptance Criteria**: Testable condition

## 3.1 Authentication Requirements

### FR-AUTH-001: User Registration

**Title**: User can create an account with email and password

**Description**: The system shall allow a new user to register by providing a unique email address and a password that meets security requirements. Upon successful registration, the system shall create a user account in the database with hashed password.

**Priority**: Mandatory

**Acceptance Criteria**:
- User can register with valid email and password
- System rejects duplicate email addresses
- Password is hashed before storage
- User receives success confirmation

---

### FR-AUTH-002: User Login

**Title**: Registered user can authenticate with credentials

**Description**: The system shall authenticate a registered user by validating their email and password. Upon successful validation, the system shall issue a JWT token containing user identification claims.

**Priority**: Mandatory

**Acceptance Criteria**:
- Valid credentials result in successful login
- Invalid credentials are rejected with error message
- JWT token is returned on successful login
- Token contains user ID claim

---

### FR-AUTH-003: User Logout

**Title**: User can terminate their session

**Description**: The system shall allow a logged-in user to logout by clearing their session token. The client shall remove the stored token from local storage.

**Priority**: Mandatory

**Acceptance Criteria**:
- Logout button/action available on all pages
- Token is cleared from client storage
- User cannot access protected pages after logout

---

### FR-AUTH-004: Password Hashing

**Title**: Passwords are securely hashed before storage

**Description**: The system shall use bcrypt algorithm with minimum cost factor of 12 to hash passwords before storing in the database. Plain-text passwords must never be stored.

**Priority**: Mandatory

**Acceptance Criteria**:
- Password hashed using bcrypt
- Hash includes salt
- Plain-text password not stored
- Verification uses constant-time comparison

---

### FR-AUTH-005: Session Management

**Title**: Authenticated sessions are maintained using JWT tokens

**Description**: The system shall issue JWT tokens upon successful login with 24-hour expiration. Subsequent requests shall include the token in Authorization header for verification.

**Priority**: Mandatory

**Acceptance Criteria**:
- Token issued on login
- Token includes expiration claim (24 hours)
- Token required for protected endpoints
- Expired tokens are rejected

---

### FR-AUTH-006: Input Validation

**Title**: Registration inputs are validated before processing

**Description**: The system shall validate email format, password length (minimum 8 characters), and password complexity (at least one letter and one number) before processing registration.

**Priority**: Mandatory

**Acceptance Criteria**:
- Invalid email format is rejected
- Password shorter than 8 characters is rejected
- Password without letter or number is rejected
- Clear error messages displayed for each validation failure
